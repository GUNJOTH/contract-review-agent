# ADR-001：保留证据优先的模块化单体

- 状态：已接受
- 日期：2026-09-11
- 范围：合同审查智能体运行层

## 背景

项目已经具备多格式解析、OCR 适配、规则快照、知识检索、模型审查、人工决定、报告和回放。核心风险不是缺少一个新的 Agent 框架，而是外部模型不确定性、证据错绑、重复任务和失败后无法恢复。仓库还要在没有 Docker daemon、Redis 或模型服务的开发机上保持可验证。

## 决策

采用模块化单体作为默认部署形态：

1. `contract_review` 保持无框架依赖的领域引擎和强类型模型。
2. FastAPI、Celery/Redis、OCR、模型、SQLite 和文件系统均是可替换适配器。
3. 审查采用显式阶段和证据门：解析质量 → 索引/检索 → 确定性规则 → 可选模型 → 人工确认 → 回放/发布。
4. 结果、请求、规则快照和外部模型交互都带版本/指纹；失败降级为可见状态，不自动通过。
5. 先以适配器方式落地 idempotency、事件账本、隐私门和观测契约，再评估是否需要引入持久化编排框架或拆分服务。

## 备选方案

### 全量迁移到 LangGraph / Semantic Kernel

不采用。它们的持久化和事件编排模式值得借鉴，但直接替换会扩大状态模型、部署依赖和回放差异；现有 `ReviewRun` 已经提供确定性状态链，迁移收益尚未被运行指标证明。

### 现在拆成微服务

不采用。当前规则库、证据、模型请求和人工决定共享同一审查边界；过早拆分会引入跨服务事务、版本漂移和难以重放的网络状态。

### 纯 Agent 驱动，规则退居提示词

不采用。合同审核的合规门禁、证据绑定和可追责性要求确定性规则先行；模型只能补充语义判断，不能替代证据和人工审批。

## 后果

正面影响：

- 领域逻辑可以离线测试和回放，外部服务不可用时仍能产出诚实的确定性结果。
- API、worker 和未来 CLI 共享同一编排，不会各自实现一套审查规则。
- 适配器边界便于逐步加入 Redis 原子幂等、OTEL 和隐私网关。

代价与风险：

- 单体发布仍需同时管理 API、worker、beat 和运行时目录。
- Redis 任务记录通过独立列表保存有界阶段事件账本；历史事件达到配置上限后按保留策略裁剪，生产侧应将事件导出到长期审计存储。
- 模型输出结构化校验已有基础，但 AI 分析接口仍有少量历史 `dict` 兼容字段，需渐进收紧。

## 验收标准

- 领域引擎测试、重放指纹和 API smoke 不依赖真实 OCR、模型或生产数据库。
- 任一模型/工具输出不能引用结果证据集合之外的 ID。
- 任务重复提交、worker 丢失、缓存写入中断和 API 未捕获异常都有可观察的错误码、日志和回滚路径。
- 异步任务相同 `Idempotency-Key` 不重复落盘/入队，阶段状态与审查运行共用 `StageEvent` 形状；外部模型输入在 PII 门禁阻断时不得发送正文。
- 在 Docker/Redis/OCR/模型环境齐备后，再执行真实联调和性能验收；本地缺失依赖不视为通过。

## 回滚

本 ADR 的实现可以按适配器逐项回滚：恢复旧缓存写入、关闭异步角色或禁用外部模型，不应删除 `ReviewResult`、`ReviewRun`、证据和审计记录。任何新事件字段必须向后兼容旧 JSON 结果。
