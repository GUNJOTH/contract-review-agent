# 合同审查智能体架构基线

## 1. 业务能力

本次建设的业务能力是：对一个合同文件包进行可追溯的文档解析、事实抽取、规则检查、跨附件一致性审查和人工确认。

### Actor

- 业务人员：上传合同包、补充文件、查看证据、提交复核。
- 法务/财税/技术审核人：确认高风险或不确定结论。
- 审查服务：解析、计算、检索、生成审核发现。

### 核心对象

```text
ContractPackage
  └── Document
        └── Page
              └── LayoutBlock / TextToken / TableCell

ContractFact ──extractedFrom──> Evidence
Finding ──triggeredBy──> Rule
Finding ──supportedBy──> Evidence
ReviewDecision ──decides──> Finding
ReviewRun ──used──> Source / Rule / Parser / Model
```

## 2. 真实数据流

```text
文件上传（写对象存储，生成哈希）
  -> 解析任务（异步）
  -> 页面和版面快照（写解析结果）
  -> 事实抽取（写事实和证据关联）
  -> 规则检查（只读事实，生成发现）
  -> RAG/LLM 语义审查（只能引用已存在证据）
  -> 人工决定（写决定历史）
  -> 报告和回放
```

原始文件、页面图像和证据定位属于不可变输入；解析结果和审核发现按运行版本保存，不覆盖旧运行。

## 3. 文档解析分层

### 文件层

保存 `file_id`、文件名、MIME、大小、SHA-256、上传来源、合同包 ID 和接收时间。

### 页面层

保存物理页码、印刷页码、页面宽高、旋转角度、渲染尺寸和质量标记。物理页码和印刷页码必须分开，避免“合同第 4 页”与 PDF 第 5 页混淆。

### 版面层

版面对象至少包括标题、段落、列表、表格、图片、印章和签名。每个对象保留页面坐标、阅读顺序、原始文本和提取方法。

### 语义层

从版面对象中形成 `Clause`、`DefinedTerm`、`CrossReference`、`AttachmentReference` 和 `ContractFact`。大模型可以辅助语义抽取，但输出必须关联证据 ID，并通过类型、格式和业务约束校验。

## 4. 证据设计原则

证据不是审核结果中的一段引用文本，而是独立的一等对象：

- 绑定不可变文件哈希；
- 绑定文档 ID、页面、版面块和词级范围；
- 同时保存原始摘录和用于展示的规范化摘录；
- 保存提取方法、解析器/OCR 版本和置信度；
- 支持文字证据、表格单元格、视觉区域、缺失附件和跨文件比较证据；
- 前端可以通过证据定位回到原文件并高亮。

跨文件结论必须至少有左右两组事实证据。例如“主合同金额与报价单金额不一致”不能只有一条引用，而要分别引用主合同和报价单。

## 5. 结果状态

```text
PASS            有充分证据且规则满足
WARN            存在风险或需要业务注意
BLOCK           按已发布规则阻断流程
UNKNOWN         证据不足、OCR 质量不足或规则无法确定
NOT_APPLICABLE  规则不适用于当前合同类型
```

模型置信度不等同于风险等级。低置信度必须进入 `UNKNOWN` 或人工复核，不得直接转为通过。

## 6. 与 Excel 规则的连接

`合同审批检查自查标准_v0.14.xlsx` 应作为规则源快照导入 `Rule`，而不是运行时直接读取单元格。每条规则至少保存：

```text
rule_id
version
category
applies_to
condition
check_method
expected_value
risk_level
required_evidence
human_review
effective_from / effective_to
source_snapshot
```

表内的 `√`、`×`、产权归属和税率属于适用性/预期值，不是审核结果。

## 7. 暂不纳入首个里程碑的能力

- 具体 OCR 厂商/模型的实际部署（当前已提供 `OCRProvider` 契约，扫描页可在注入同版本提供方后形成坐标证据）；
- 表格和合并单元格结构识别；
- 印章真实性判断；
- 外部 ERP/订单系统连接；
- 生产数据库、权限和前端页面；
- RAG 召回质量评测集。

这些能力必须在解析和证据契约稳定后接入，避免模型先于证据层产生不可回放的结论。

## 8. 当前代码实现

当前 `src/contract_review` 已形成四个可替换层：

1. `parser.py`：使用 PyMuPDF 读取数字 PDF 的页面、文字块和词级坐标；使用 DOCX XML 读取段落和表格单元格；使用 XLSX XML 读取工作表、单元格地址和原始值。分别生成页坐标证据、文档块证据或表格单元格证据。扫描页只设置 `needs_ocr`，不把空结果当作识别结果；未缓存的 XLSX 公式不会被本地自行计算。
2. `models.py`：用 Pydantic 约束证据契约。页码定位、坐标、表格单元格、缺失附件和外部 URI 各有不同必填字段；文字/表格/视觉证据必须绑定文档哈希。
3. `review.py`：先做确定性检查。附件缺失输出 `MISSING_ARTIFACT + UNKNOWN`；跨文件事实比较保留左右事实的全部证据；事实类型或单位不兼容时不比较。
4. `run.py` 与 `replay.py`：以不可变输入快照创建审查运行，并把状态转移追加到 `ReviewTransition`。回放指纹包含文件哈希、规则快照、解析器版本、模型版本和配置；重放还会比较最终结果指纹。
5. `knowledge.py`：把文本块和规则快照切成 `KnowledgeChunk`，用可替换的检索器产生 `RetrievalTrace`。当前提供确定性的词法基线，生产环境可替换向量检索，但必须保留同样的证据 ID 和版本信息。
6. `pipeline.py` 与 `store.py`：编排完整运行，逐条执行规则，输出人工复核队列，并将运行结果以写一次 JSON 审计工件落盘。工件载荷和结果指纹都校验后才可读取。
7. `semantic.py`：约束外部语义模型响应。模型只能返回已请求的规则和已存在的证据 ID；响应还必须携带与本次召回片段、提示词版本和模型版本一致的请求指纹，低置信度自动降为 `UNKNOWN`。

证据对象的最小关系可以表示为：

```text
原始文件 --SHA-256--> Document
Document --page/box/token--> Evidence
Evidence --supports--> ContractFact
Rule + ContractFact + Evidence --produces--> Finding
Finding --recorded_in--> ReviewRun
```

## 9. RAG 和大模型的边界

RAG 只负责从已登记的条款、规则和历史案例中召回候选依据；召回结果必须带知识库文档版本和片段定位。大模型可以做合同类型判定、条款归类、事实抽取和语义风险建议，但输出必须先通过结构化模型校验，再检查每个结论是否引用已存在的 `evidence_id`。

因此建议的调用顺序是：

```text
解析/OCR -> 证据登记 -> 事实抽取 -> 规则检查 -> RAG 召回 -> LLM 判断 -> Finding -> 人工确认
```

不能让模型直接读取向量片段后生成“通过”；证据缺失、OCR 质量不足、规则适用性不明或模型引用不存在时，结果应进入 `UNKNOWN`/人工复核。

## 10. 审查结果与人工边界

运行不是把模型回答写进一个总字段，而是保留四类可核验记录：

- 机器发现：规则、状态、风险等级、原因、事实 ID 和证据 ID；
- 检索轨迹：查询、索引版本、命中片段、分数和命中片段的证据 ID；
- 人工决定：审核人、角色、决定、说明和所引用证据；
- 运行审计：阶段转移、输入哈希、规则/模型/解析器版本、结果指纹和载荷哈希；人工决定和最终确认以不可覆盖 revision 追加，不覆盖基础审查工件。

因此，即使某条规则还没有实现，也会输出 `UNKNOWN` 并进入人工队列；只有所有可行动发现都有明确决定，运行才允许进入 `FINALIZED`。这比把“模型没有发现问题”当作通过更安全，也更适合后续质量评估。

Excel 规则已从 `合同审批检查自查标准_v0.14.xlsx` 生成 `data/contract_rules_v0.14.json`。该 JSON 是运行时规则快照，保留原表哈希、`Sheet1!A1:M54`、每条规则的原始单元格定位和适用性字段；原始 Excel 仍是只读来源。
